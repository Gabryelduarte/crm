# Firestore model and security review

## Assumptions

- The website uses Firebase Authentication email/password; each authenticated user's `uid` is the owner boundary.
- The frontend reads and writes the shared state document at `userStates/{ownerUid}`. The `ownerUid` is the administrator UID already associated with this project's local account state.
- The administrator's access list is stored separately at `userStates/{ownerUid}/access/permissions`; only the administrator can read or modify it.
- A shared member is authorized by an exact Firebase Auth email claim match against `memberEmails` and must have `email_verified == true`. Members can edit the shared state but cannot read, list, or modify the access list.
- The document contains `ownerUid`, `updatedAt`, and a `state` map. The state map contains list fields: `vendas`, `emProducao`, `pagamentos`, `compras`, `outrosGastos`, `estoque`, `custosFabricacao`, `costureiras`, and `log`.
- Inventory entries may contain a base64 image string. Firestore has a 1 MiB document limit, so very large accumulated state or photos can make a write fail.
- The client updates the complete state document. Record-level shapes are normalized in the frontend; rules bound top-level fields and list lengths but cannot iterate over every map inside arbitrary lists.

## Access and attack checks

- Unauthenticated get/create/update: denied by authentication and owner/member checks.
- User A reading another owner's state without an invited verified email: denied by `isSharedMember`.
- Uninvited, unverified, or other users cannot read/write shared state; a verified invited email can read and edit only the configured owner's state.
- A shared member cannot list user-state documents or read/list/write the access list.
- Only the configured owner UID can invite or revoke members; access-list size is limited to 50.
- Listing all user-state documents: denied; the app uses a direct document get.
- Creating or updating extra top-level document/state keys: denied by `hasOnly` checks.
- Removing a required state list, changing its type, or exceeding a list bound: denied on both create and update.
- Changing `ownerUid` during update: denied by `uidNotModified`.
- Deleting state or permissions: denied; the app has no whole-space delete operation.
- Arbitrary malformed fields inside a user's own state lists: not deeply inspected by Firestore rules; access remains confined to that same user's document. The frontend remains responsible for record validation.
- Oversized individual strings or images: bounded by Firestore's document-size limit, but may reject saves. A dedicated Storage image flow is a future improvement if photos approach that limit.
